# Ревью производительности · 2.5.2

Проверены захват PCM, временные записи и распознавание, очереди и отмена, SSE, генерация контекста, SwiftUI, окна, индикатор звука и настройки. Основная подтверждённая проблема — слишком частые обновления интерфейса при получении ответа. Исправления уменьшают эту работу, сохраняя полный текст и сборку длинных вопросов.

## Исправлено

| Приоритет | Наблюдение | Изменение |
| --- | --- | --- |
| Высокий | Каждый фрагмент SSE создавал отдельную MainActor-задачу и обновлял весь наблюдающий интерфейс | [StreamingTextDelivery](../Sources/Support/StreamingTextDelivery.swift) объединяет промежуточные снимки: начало сразу, продолжение с интервалом 50 мс. Ожидает не более одного снимка |
| Средний | При ошибке до выполнения MainActor-задачи последний текст мог исчезнуть | Ожидающий фрагмент доставляется перед ошибкой; полный успешный ответ публикуется сразу |
| Средний | [RecordedSpeechStream](../Sources/Transcription/RecordedSpeechStream.swift) опрашивал часы 20 раз в секунду даже без аудио | Одноразовое ожидание ближайшей границы. Нет открытой реплики — нет опроса |
| Средний | Индикатор публиковал повторную тишину и обновлялся за скрытым окном | [AudioActivity](../Sources/Assistant/AssistantController.swift) объединяет незаметные изменения, сохраняет последний уровень и публикует его при возврате окна |
| Низкий | Ввод резюме, контекста и других настроек повторно применял свойства нативных окон | [AppDelegate](../Sources/App/AppDelegate.swift) подписан только на три относящиеся к окнам настройки, с удалением повторов |

Объединение обновлений применяется также к шаблону встречи. Сетевые запросы, конец вопроса и первый фрагмент не ждут дополнительной задержки 50 мс. Окончания ответов, порядок вопросов, повтор после ошибки и отмена проверяются отдельно.

## Измерения

Локальная macOS, Apple Silicon, 16 ГБ памяти, 10 логических ядер. Сравнение исходников 2.5.1 и 2.5.2: один и тот же инструмент, оптимизированная компиляция `swiftc -O`, по два прогона каждого варианта. Другие приложения не завершались.

Стресс-сценарий: окно 1100 × 720, 600 синтетических фрагментов текста с запрошенным интервалом 5 мс. Время CPU — сумма user + system процесса через `getrusage`, а не длительность сетевого ответа. Фактическая длительность сценария зависит от планировщика.

| Метрика | До | После |
| --- | --- | --- |
| CPU на один поток из 600 фрагментов, два прогона | 3,77 / 4,15 с | 1,32 / 1,05 с |
| Публикации состояния ответа | 604 / 604 | 93 / 86 |
| Опрос часов без аудиобуферов, примерно за 2 с | около 43 | 0 |
| Публикации 100 одинаковых нулевых уровней, регрессионный тест | 100 | 0 |

По среднему двух прогонов CPU стресс-сценария уменьшился примерно на **70%**, количество публикаций — примерно на **85%**. Это измерение конкретного потока текста, не снижение общей нагрузки Mac на 70% и не оценка энергопотребления полного звонка. Прогоны не включают реальное распознавание и API.

В отдельном 16-секундном наблюдении работающего Dakt 2.5.1 с системным аудио: **1,9–2,9% одного ядра**, около **50 МБ physical footprint**. В тот момент swap всей системы занимал около **8,9 ГБ**; текущих swap-in/out за интервалы `top` не наблюдалось. Наличие swap само по себе не доказывает, что торможение вызвал Dakt. Для редкого зависания нужен замер именно во время него.

## Проверенные гипотезы и ограничения

- **Захват.** Уже используется видео 2 × 2 при 1 кадре/с, аудио 48 кГц stereo. Копия PCM необходима: ScreenCaptureKit переиспользует буфер после callback. 200 000 расчётов уровня по 480 stereo-кадрам заняли около 0,19 с CPU; это не подтвердило поиск пика как основное узкое место. Формат и качество звука сохранены.
- **Распознавание.** Одна активная обработка, максимум восемь ожидающих частей, ограниченные файлы и удаление после обработки. Модель SpeechAnalyzer работает через системные службы, поэтому CPU одного Dakt не описывает всю стоимость распознавания. Политика удержания модели сохранена ради быстрого следующего вопроса.
- **Окно.** Статический замок не показал непрерывной загрузки. В коротких A/B-прогонах выключение размытия поверх движущегося фона меняло общий CPU WindowServer примерно на 1–2 процентных пункта одного ядра. WindowServer обслуживает весь рабочий стол; этого недостаточно для вывода о главной причине нагрузки. Размытие и оформление сохранены.
- **Память.** История ограничена 80 репликами и 20 ответами, предварительный аудиобуфер — примерно 0,25 с. Нарастание памяти в этих коротких сценариях не установлено; многочасовой тест утечек не выполнялся.
- **Очередь ответов.** Ожидающие текстовые вопросы пока не имеют жёсткого лимита. При длительно недоступном API и продолжающемся прослушивании очередь может расти. Это отдельный риск длительной сессии; в текущих измерениях он не был источником высокой нагрузки. Ограничивать её с молчаливым отбрасыванием вопросов нельзя.
- **Область проверки.** Целые вопросы, короткие паузы, ошибки, отмена, скрытие и замок покрыты регрессионными проверками. Нагрузка настоящего звонка во всех программах и работа на физическом Intel Mac отдельно не измерялись.

Итоговая проверка: **79 автоматических тестов**, нативные события скрытия/замка в нескольких размерах и отдельный прогон 25,79-секундной синтетической записи через настоящий SpeechAnalyzer и API. В последнем получены два целых вопроса и два завершённых ответа, максимум один запрос одновременно, без ошибок. Этот функциональный прогон не использовался для расчёта снижения CPU.

## Повторить измерения

Нужны macOS с графической сессией и инструменты сборки проекта. Проверка использует только синтетические данные: без захвата, ключей, пользовательских настроек и API. На время теста появляются окна.

```sh
./Tools/performance-check.sh
```

Бинарник и строки JSON сохраняются в `.build/performance-check/`. Метрика `cpu_percent_one_core` относит 100% к одному ядру. `peak_rss_mb` — максимальный RSS процесса к этому моменту, не текущая память отдельного сценария. WindowServer включает работу других приложений.

Для отдельной копии исходников и каталога результатов:

```sh
./Tools/performance-check.sh /путь/к/копии/проекта .build/performance-before
./Tools/performance-check.sh . .build/performance-after
```

Прогоны выполняйте последовательно. Во время измерения не запускайте сборки, GUI-тесты или вторую копию теста. Сравнивайте одинаковый сценарий и несколько прогонов, а не максимумы общего Activity Monitor.

```sh
swift test --jobs 2
.build/debug/DaktRecorder --render-previews .build/performance-previews
```
